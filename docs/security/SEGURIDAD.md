# Seguridad y límites de la validación

- Auth0 verifica los tokens de acceso de la API. El código restringe RS256 y exige un `sub` válido; firma, emisor, audiencia y vigencia se verifican mediante el SDK y JWKS. Se exige una audiencia API distinta del client ID configurado. La correcta separación de audiencias de todos los clientes debe comprobarse en el tenant real: no existe un atributo JWT universal que distinga por sí solo todos los ID tokens de todos los access tokens.
- Los tests firman tokens con claves sintéticas y simulan discovery/JWKS; no prueban Auth0 real, su red, configuración o ciclo de rotación en producción. No se implementan login, contraseñas, alta, enlace por email ni vinculación de prerregistro.
- Los dos pools usan cuentas distintas y el código rechaza owner/migrador, roles privilegiados y varias membresías incompatibles. `lawware_auth_service` tiene permisos amplios sobre `usuario` en el baseline; se requiere revisión posterior de permisos directos, roles y TLS de la infraestructura definitiva.
- `app.user_id` y los demás GUC no son identidad fuerte. Un atacante con SQL arbitrario o credenciales de servicio puede falsificarlos. El caso de uso debe establecerlos solo tras verificar identidad; las pruebas locales de reutilización no garantizan el aislamiento de todas las operaciones futuras.
- Los eventos de error no registran headers, tokens, body, query ni detalles de excepciones. Los 401 se registran como `auth.unverified` porque también pueden reflejar indisponibilidad de JWKS; no se clasifican como ataques confirmados. El registro estructurado en stdout sucede fuera de la transacción revertida, pero falta implementar y verificar almacenamiento externo, lecturas sensibles, retención, integridad y alertas.
- El límite de cuerpo y CORS no son defensas completas de autorización ni una política legal. Las decisiones de privacidad y retención siguen abiertas; no se ha aprobado producción.
